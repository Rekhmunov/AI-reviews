# ТЗ: Восстановление КИЗ/ШК при приёмке возвратов на склад

**Статус:** к реализации  
**Контур:** Остатки → Добавить на склад → тип «Возврат» + поверх — «Восстановить данные»  
**Связанные модули:** `supply-balances` (приход), `wb_fbs_returns` (журнал/печать возвратов WB)

---

## 1. Цель

Дать оператору склада **одно рабочее место** приёмки возвратов:

1. **Happy path** — как сейчас: скан ШК или КИЗ → товар в список → «Сохранить» → остатки.
2. **Exception path** — потерян/повреждён КИЗ или ШК: кнопка **«Восстановить данные»** открывает поверх (не закрывая приёмку) инструмент поиска по стикеру возврата / КИЗ с печатью маркировки и ШК; после печати оператор продолжает приёмку в той же модалке «Добавить на склад».

Не заставлять ходить в «ВБ ФБС → Возвраты» для ежедневной работы.

---

## 2. Роли и сценарии

### 2.1. Оператор склада (основной пользователь)

| # | Сценарий | Ожидание |
|---|----------|----------|
| A | На товаре есть читаемый ШК или КИЗ | Скан в «Добавить на склад» (Возврат) → товар +1 → Сохранить |
| B | Нет КИЗ / КИЗ не читается, есть стикер возврата WB | «Восстановить данные» → скан стикера возврата → печать КИЗ (и/или ШК) → закрыть → скан в приёмку |
| C | Нет ШК на товаре, нужно наклеить заново | Restore → найти возврат → «Печать ШК» → закрыть → скан ШК в приёмку |
| D | КИЗ есть, но этикетка порвана; нужно перепечатать | Restore → скан КИЗ → «Печать маркировки» → закрыть → приёмка |
| E | Стикер возврата не найден в кэше | Сообщение: нет в уже загруженных отчётах — сначала «ВБ ФБС → Возвраты → Синхр. WB»; приёмку по ШК/КИЗ не блокировать |

### 2.2. Админ / старший

Полный журнал «ВБ ФБС → Возвраты» (CSV, фильтры, ручной sync по источнику) **остаётся** без изменения поведения для админских задач. Складской restore — упрощённый операторский слой поверх той же серверной логики.

---

## 3. Текущее состояние (as-is)

### 3.1. Остатки → Добавить на склад

- UI: `#supplyStockReceiptModal`, тип `#supplyStockReceiptKind` = `receipt` | `return`.
- Скан: `#supplyStockReceiptScan` → `processSupplyStockReceiptScan()` — матч по каталогу товаров (ШК / GTIN из КИЗ).
- Сохранение: `POST /api/supply-balances/receipt`.
- **Ограничения:** стикер возврата WB не распознаётся; печати КИЗ/ШК нет; тип «Возврат» на бэкенде сейчас по сути тот же `manual_receipt` (косметика в UI).

### 3.2. ВБ ФБС → Возвраты

- UI: `#wbFbsKizRestoreModal` (`openWbFbsKizRestoreModal`).
- Sync: `POST /api/wb-fbs/returns/sync` + poll status — **один** `source_id`.
- Скан: `POST /api/wb-fbs/returns/scan` — стикер возврата / стикер сборки / КИЗ.
- Печать: `GET /api/wb-fbs/returns/print` (DataMatrix), ШК из `catalog_barcodes`.
- **Ограничения:** не пишет в остатки; sync по одному источнику; агрессивный multi-window sync бьёт в Analytics 429 на «тяжёлых» кабинетах.

## 4. Продуктовое решение (to-be)

```
┌─────────────────────────────────────────────┐
│  Добавить на склад  [тип: Возврат ▾]        │
│  [Скан ШК/КИЗ…………]                         │
│  [ Восстановить данные ]  ← только Return   │
│  список позиций…          [Сохранить]       │
└─────────────────────────────────────────────┘
              │ открыть поверх (z-index выше)
              ▼
┌─────────────────────────────────────────────┐
│  Восстановить данные (возврат WB)     [✕]   │
│  источники: фоновая очередь sync (не блок)  │

│  карточка результата + Печать КИЗ / ШК      │
└─────────────────────────────────────────────┘
```

После закрытия restore модалка приёмки **остаётся открытой**, фокус возвращается в `#supplyStockReceiptScan`.

## 5. UI / UX

### 5.1. Кнопка «Восстановить данные»

- Место: модалка `#supplyStockReceiptModal`, блок сканирования (рядом с `#supplyStockReceiptScan` или под ним).
- Видимость: **только** если `#supplyStockReceiptKind === "return"`.
- При переключении на «Приход» — кнопка скрыта; если restore открыт — закрыть restore.
- Стиль: secondary / outline, не конкурирует с primary «Сохранить».
- id (предложение): `#supplyStockReceiptRestoreBtn`.

### 5.2. Модалка «Восстановить данные»

Новая модалка (не переиспользовать целиком тяжёлый админский `#wbFbsKizRestoreModal` с таблицей/CSV/календарём), но **те же API и печать**.

Предлагаемый id: `#supplyStockReturnRestoreModal`.

**Состав первого экрана:**

1. Заголовок: «Восстановить данные».
2. Подзаголовок (1 строка): «Сканируйте стикер возврата WB или КИЗ для печати».
3. Компактный статус кэша (без sync), например:  
   `Данные из ВБ ФБС → Возвраты` / `кэш пуст — сначала синхронизируйте в ВБ ФБС → Возвраты`.
4. Поле скана (Enter) — аналог `#wbFbsKizRestoreScan`.
5. Область результата (пусто / карточка / ошибка).
6. Кнопка ✕ — закрыть только restore.

**Карточка результата после успешного скана:**

- Заказ / стикер возврата / тип скана (Возврат | Маркировка | Стикер сборки).
- Товар: фото (если есть), название, артикул.
- КИЗ: полный код или «не найден».
- Кнопки:
  - **Печать маркировки** — enabled, если есть КИЗ; иначе disabled + подсказка.
  - **Печать ШК** — enabled, если есть barcodes в каталоге товаров; иначе disabled + подсказка.
- При нескольких ШК — тот же выбор, что в ВБ ФБС (`#wbFbsReturnsBarcodeModal` или аналог поверх restore).

**Не включать в v1 складского restore:** таблицу журнала, CSV, календарь, бесконечный скролл, фильтры типов (опционально позже).

### 5.3. Слои модалок (важно)

- `#supplyStockReceiptModal` остаётся открытой (`hidden` не ставить).
- `#supplyStockReturnRestoreModal` — поверх (выше z-index), `aria-modal="true"`.
- Закрытие restore **не** вызывает `closeSupplyStockReceiptModal`.
- Клик по оверлею restore: либо не закрывать (как у ВБ ФБС Возвраты), либо закрывать только restore — зафиксировать в реализации: **не закрывать по клику на оверлей** (меньше случайных закрытий со сканера).
- Esc: закрывает только верхнюю (restore), если она открыта.

### 5.4. После печати

- Печать — как сейчас (окно/iframe DataMatrix или JsBarcode 58×40).
- Restore **не** автозакрывается после печати (оператор может напечатать и КИЗ, и ШК).
- Подсказка в info: «Распечатайте этикетку, затем отсканируйте её в «Добавить на склад»».

## 6. Поведение скана в restore

Классификация — **та же**, что `process_return_scan` / `POST /api/wb-fbs/returns/scan`:

1. Похоже на КИЗ → `kiz` (перепечатка).
2. Есть в кэше `wb_fbs_goods_returns` → `return_sticker`.
3. Стикер сборки в `wb_fbs_orders` → `assembly_sticker`.
4. Иначе — not_found.

### 6.1. Отличие от админской модалки: все источники, без sync

Скан и поиск выполняются **по всем WB FBS-источникам** владельца (куда есть доступ), **только по уже сохранённым в БД** данным (`wb_fbs_goods_returns`, `wb_fbs_orders`, локальные КИЗ).

**Restore не вызывает** `POST /api/wb-fbs/returns/sync` и не ставит sync-all очередь.  
Актуальный отчёт goods-return оператор/админ заранее подтягивает в **«ВБ ФБС → Возвраты → Синхр. WB»**.

Варианты реализации скана (предпочтение A):

| | Подход | Плюсы | Минусы |
|---|--------|-------|--------|
| **A** | `POST /api/wb-fbs/returns/restore/scan` — сервер ищет по всем source_id в локальном кэше | Один round-trip, быстро | Нужна дедупликация ambiguous |
| B | Клиент дергает `/scan` по списку source_id | Меньше нового API | Медленнее |

**Правила match:**

- Первый однозначный hit → результат + `source_id` + имя источника.
- Несколько разных заказов/товаров в разных источниках → `ambiguous`, без записи, текст «Найдено в нескольких кабинетах».
- Duplicate в журнале сканов — **карточку для печати всё равно отдать** (`duplicate: true`). См. §7.3.
- Not found в кэше → понятный `detail`: синхронизируйте отчёт в ВБ ФБС → Возвраты.

Запись в `wb_fbs_return_scans`:

- **Да** при новом успешном скане (единый журнал).
- При duplicate — без новой строки, payload для печати вернуть.

## 7. API

### 7.1. Существующие (переиспользовать)

| Метод | Путь | Назначение |
|-------|------|------------|
| POST | `/api/wb-fbs/returns/scan` | скан одного source (логика match/КИЗ) — можно вызвать изнутри restore/scan |
| GET | `/api/wb-fbs/returns/print` | PNG DataMatrix |
| GET | `/api/supply-balances/visibility` | каталог + barcodes (уже для приёмки) |
| POST | `/api/wb-fbs/returns/sync` | **только** админская «ВБ ФБС → Возвраты», не из restore |

### 7.2. Новые / расширения

#### 7.2.1. Скан по всем источникам в локальном кэше (+ печать при duplicate)

`POST /api/wb-fbs/returns/restore/scan`

- Ищет **только в БД** (`wb_fbs_goods_returns` / orders / КИЗ) по всем доступным source_id.
- **Не** ходит в WB Analytics goods-return.
- Ответ совместим по полям с текущим `/returns/scan` result item + `source_id`, `source_name`.

Body:

```json
{ "scan": "…" }
```

Успех:

```json
{
  "ok": true,
  "duplicate": false,
  "item": { /* карточка */ },
  "source_id": 21,
  "source_name": "…"
}
```

Duplicate (уже в журнале сканов) — всё равно отдать карточку для печати:

```json
{
  "ok": true,
  "duplicate": true,
  "item": { /* те же поля для печати */ },
  "message": "Уже был в журнале — можно распечатать снова"
}
```

not_found / ambiguous — 404 с понятным `detail` (для not_found указать: обновите отчёт в ВБ ФБС → Возвраты).

Печать: существующий `GET /returns/print?…`.

#### 7.2.2. (Опционально) Сводка кэша для статус-строки

`GET /api/wb-fbs/returns/restore/cache-info`

```json
{
  "sources": [
    { "source_id": 21, "name": "…", "goods_rows": 120, "last_synced_at": "…" }
  ],
  "total_goods_rows": 120
}
```

Без вызовов WB. Нужен только для подсказки «кэш пуст / есть данные».

## 8. Политика данных: только ранее скачанные отчёты

### 8.1. Разделение ролей

| Где | Что делает |
|-----|------------|
| **ВБ ФБС → Возвраты → Синхр. WB** | Единственное место загрузки goods-return с WB в `wb_fbs_goods_returns` |
| **Остатки → Восстановить данные** | Только чтение кэша + журнал сканов + печать |

### 8.2. Запрещено в restore v1

- Любой `sync` / `sync-all` / автозагрузка отчёта с Analytics API.
- Ожидание WB при открытии модалки.
- Кнопка «Обновить из WB» внутри restore (чтобы не смешивать роли; обновление — в ВБ ФБС).

### 8.3. Зачем так (скорость и стабильность)

- Открытие restore и скан — **мгновенно** (локальная БД), без минут ожидания окон 90 дней.
- Нет 429/504 из-за Analytics в момент приёмки на складе.
- Операторский ритм: утром/накануне админ или старший синхронизировал кабинеты в ВБ ФБС; склад весь день только сканирует и печатает.
- Цена: если отчёт не синхронизировали — стикер возврата может не найтись, пока не сделают sync в ВБ ФБС. Это явный и понятный контракт.

## 9. Связь с приёмкой на склад

### 9.1. Что не менять в v1

- Логику `processSupplyStockReceiptScan` (ШК / GTIN → qty++).
- `POST /api/supply-balances/receipt` контракт (можно позже добавить `kind=return` — вне обязательного scope v1).

### 9.2. Операторский цикл после restore

1. Печать КИЗ или ШК в restore.
2. Закрыть restore.
3. Отсканировать **распечатанный** ШК или КИЗ в `#supplyStockReceiptScan`.
4. Товар появляется в списке → «Сохранить».

Автоматически добавлять товар в список приёмки из карточки restore в **v1 не требуется** (меньше риска неверного qty / неверный товар). Опционально v1.1: кнопка «Добавить в приёмку» на карточке.

## 10. Нефункциональные требования

- Не ломать скорость скана в приёмке (restore — отдельный поток).
- Открытие restore и `restore/scan` — только локальная БД, ответ обычно << 1 с; **никаких** вызовов WB Analytics из restore.
- Мобильная ширина ≥375px: restore читаем, кнопки печати крупными.
- Доступ: те же права, что просмотр WB FBS / остатков.
- Логирование: scan hit/miss/ambiguous/duplicate (без секретов ключей).

---

## 11. Вне scope (не делать в этой задаче)

- Ozon возвраты.
- Sync/загрузка goods-return из модалки restore.
- Автоматическое списание/перемещение кроме ручного «Сохранить» приёмки.
- Замена админской модалки ВБ ФБС.
- Обязательный КИЗ для немаркируемых товаров.
- Лечение 429 кабинета / hydrate — отдельные задачи (на restore не влияют, т.к. WB не вызывается).

## 12. Критерии приёмки

1. При типе «Приход» кнопки «Восстановить данные» нет.
2. При типе «Возврат» кнопка есть; открывает restore **поверх** приёмки; приёмка не закрывается.
3. Закрытие restore возвращает фокус в скан приёмки; список позиций приёмки не сбрасывается.
4. Скан стикера возврата (если строка уже есть в `wb_fbs_goods_returns` любого источника) показывает карточку с печатью КИЗ/ШК (если данные есть).
5. Скан КИЗ позволяет перепечатать маркировку.
6. При открытии restore **нет** запросов sync к WB; скан доступен сразу.
7. Network tab / логи: из restore не уходит `POST /returns/sync`.
8. Happy path приёмки по ШК/КИЗ без входа в restore работает как раньше.
9. Админская «ВБ ФБС → Возвраты» не регрессирует и остаётся местом синхронизации отчётов.

## 16. Резюме одной фразой

В «Добавить на склад → Возврат» остаётся быстрый скан ШК/КИЗ; «Восстановить данные» поверх ищет стикер/КИЗ **по уже скачанным отчётам всех кабинетов** и даёт печать — без нового sync и без закрытия приёмки.
